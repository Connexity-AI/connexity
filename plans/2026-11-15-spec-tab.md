# Spec tab on the agent page

- **Owner:** Dmytro
- **Slice:** Demo milestone, roadmap feature "Spec tab on the agent page (read-only)"
  (10.121). It is part 3 of the Spec epic (10.11), moved into the Demo milestone on
  2026-11-15 to follow Clarifications (10.12).
- **Design:** `designs/04-agent-profile-tabs.md` (Spec tab), `05-spec-groups.md` (fixed
  categories, no "Carried over"), `06-categories-everywhere.md` and `12-adjustments.md`
  item 13 (no spec yet). Screen: `designs/screens/Connexity Agent Profile.dc.html`, the
  Spec tab.
- **MCP:** `get_spec` gains what the tab shows: `compare`, and per rule who answered
  it and whether it is in conflict. Through MCP the assistant sees the same comparison
  and sources as the person.

## Goal

On the agent page, the person sees in seconds what the agent is supposed to do: its
rules, grouped by the fixed categories, each with where it came from. They can see what
changed against an earlier spec version. The demo shows the answer from step 4 as a
rule "From a clarification".

## What exists

- **Specs** (10.11): versions per agent, rules in the fixed categories with source,
  quote, `touches` and a key that stays the same across versions.
- **Answers:** rules from answered clarifications (10.12), with the clarification's
  id. A clarification with `replaces_key` is a question about an existing rule.
- **Web route:** `GET /agents/{id}/spec?version=` already returns a version's rules
  grouped, its state and its summary.
- **The agent page** (10.112) has Overview and Calls tabs via `?tab=`.

## Changes

### The Spec tab

A third tab, after Overview and Calls, labelled with its rule count ("Spec 14"),
at `?tab=spec`.

- **No spec yet:** the calm empty state from item 13, with no button: "No spec yet. Your
  assistant writes it from the agent's prompt." (question 4).
- **Tiles:**
  - Rules;
  - From the prompt;
  - From clarifications;
  - In conflict (warning colour when above 0);
  - Open clarifications, shown as a plain number. It has no link until the Action items
    page exists (10.122, rule 14).
- **Version line:** "Version 3 · agent version 14, since 6 Nov" (question 1), with the
  picker on the right:
  - "Version 3 only" (the default);
  - "Compare with version 2", "Compare with version 1", and so on, newest first.
- **Comparing** (`?compare=2`) compares the latest version with the one picked:
  - the tiles become Kept, Added and Dropped;
  - a "Show changes only" switch hides kept rules;
  - added rules carry "Added", and dropped rules show struck through with "Dropped" in
    their category;
  - a rule whose text changed under the same key reads as the old text dropped and the
    new text added (question 3).
- **Rules grouped by the fixed categories,** in their order, empty ones left out. Each
  group is collapsed by default to its name and count, with markers such as "1 in
  conflict", "2 added" and "1 dropped".
- **Inside a group,** one compact row per rule:
  - the rule;
  - its `touches` marker (Money, Safety, Compliance);
  - a muted source line: "From the prompt", or "From a clarification, answered by
    Dmytro on 15 Nov" (question 2).
- **"In conflict":** a rule that an open or parked clarification replaces carries "In
  conflict" and the line "The new prompt says otherwise". The design's "Open the
  clarification" link waits for 10.122.
- **Sort:** rules in conflict first, then rules that touch money, safety or compliance,
  then the spec's own order.
- **Read only.** Nothing on the tab writes.

### The API (web and MCP)

- **`GET /agents/{id}/spec` gains `compare`:** an earlier version of the agent's spec.
  The answer is the latest version, plus:
  - per rule, its change: kept, added or (for rules only in the earlier version)
    dropped;
  - counts of kept, added and dropped.
  An unknown `compare` answers 404.
- **Each rule gains** `answered_by` and `answered_at` for a rule from a clarification,
  and `in_conflict`.
- **The spec gains:**
  - `versions`: every version, newest first, with its number, agent version, origin and
    date, for the picker;
  - counts from the prompt, from clarifications and in conflict, beside the open count
    from 10.12.
- **`get_spec` (MCP)** gains the same `compare` and fields, and a rule: "In conflict
  means an open question replaces this rule; answering it changes the rule."

## Questions

1. **Which version the version line names.** The design says "Version 14 · live since 6
   Nov", which is the agent version. Spec versions are numbered separately, and one
   agent version can have several: written, then answered. Recommend "Version 3 · agent
   version 14, since 6 Nov", with the picker listing spec versions. Answers would
   otherwise all look like "version 14".
2. **The source line for an answered rule.** The design has "answered by your assistant"
   or "by Alex". Answers are recorded as the person's, with the assistant that acted.
   Recommend "From a clarification, answered by Dmytro on 15 Nov". The alternative,
   "answered by Dmytro through Claude Code", is longer; the assistant is in the decision
   record.
3. **A rule whose text changed under the same key** (a replaced answer): recommend
   showing the old text as dropped and the new one as added. That needs no new marker,
   and the design has no "Changed".
4. **The empty state's second clause,** "until then, checks that need a spec are paused
   for this agent", is not true: no check needs a spec yet. Recommend leaving it out
   until one does, and adding that to `12-adjustments.md` so the design matches.
5. **"Needs review"** (the agent moved to a newer version than its spec was written for)
   is not in the design. Recommend leaving it off the tab for now; the assistant sees it
   through MCP. Showing it would start in the design.

## Out of scope

- The Action items page and its links (10.122).
- The Issues and Tests tabs, and the score.
- "Needs review" on screen (question 5).
- Editing rules (never).

## Risks

- **A long spec.** 100 or more rules are loaded at once. Groups are collapsed, so the
  page stays short, and one query reads them.
- **Comparing reads two versions' rules.** Two queries; fine.
