# The Work page

- **Owner:** Dmytro
- **Slice:** Demo milestone, roadmap feature "Work page" (10.127). It shows the tasks of
  10.124 to 10.126 (#211, #212, #213).
- **Design:** `designs/16-work.md`, its decisions in `docs-internal/work.md`, and the
  screens `designs/screens/Connexity Work.dc.html` and `Connexity Sidebar.dc.html`
  (2026-11-16 export). Where the export and the prompt differ, the prompt wins: a warm
  pause icon, "Blocks" capitalised, "To do".
- **MCP:** `list_tasks`, which reads the same list without taking a task (question 6).

## Goal

The person opens Connexity and sees in one glance what their AI assistants are working
on, what comes next, and what waits for them. It is one ordered list: the same list,
in the same order, that `get_next_task` hands out from. It must look good enough to
explain Connexity in sales (decision 4).

## What exists

- **The tasks** (10.124 to 10.126):
  - `work_list` sorts them;
  - `assistant_task` records who took each one, in which session, and what became of
    it;
  - each task knows what it blocks and what blocks it.
- **The app today:**
  - `/` is the Readiness screen (getting started);
  - the sidebar has Action items, Agents, Calls and Issues;
  - there is no Home dashboard and no Roadmap page yet.

## Changes

### The backend

- **`GET /work`** (web, cookie auth) answers the page:
  - `in_progress`: tasks an assistant holds, with the person, assistant, session and
    when it was taken; then tasks waiting for the person (open questions, an issue fix
    whose rest is theirs), each with its action;
  - `to_do`: every other task in Connexity's order, each with its type, line,
    position, and Blocks and Blocked by, as keys and titles;
  - `done`: the last 7 days, newest first, each with what was done, by whom and when
    (question 3);
  - `sessions`: the sessions working now ("Claude Code · Onboarding"), for the page
    bar's line and its hover.
- **It reuses `work_list` and `assistant_task`.** Nothing new is stored, so the page and
  the assistant never disagree on the order.

### The page, `/work`

As designed, within the design system, dark and light:
- **The page bar:** "Work", and a muted, dotted-underlined line "2 sessions working".
  Hovering it lists each session and its task. "No assistant working" when none is.
- **"Assistant tasks"**, with the line "Your assistant works down this list from the
  top." Reordering is not built (question 2), so the line does not offer it.
- **In progress, then To do**, each a card with rows. A row has:
  - the marker: a spinning ring for in progress, a warm pause for waiting for you, a
    lock for blocked (warm when its blocker waits for the person);
  - the type icon in a tinted square;
  - the sentence;
  - the muted second line ("Issue fix · Critical · 23 calls");
  - "Blocked by: …" as a third line when blocked;
  - on the right, the chip: initial, "Alex's Claude Code · Onboarding".
- **Waiting for you:** the warm tint and bar, the warm chip "Waiting for you", and a
  quiet link under it:
  - "Answer questions →" opens the agent's questions on Action items, until 10.128
    brings the cards to Work (question 4);
  - an issue fix waiting for the person links to its issue.
- **Hover** on a blocker or a blocked row highlights the other side with the thin warm
  bar.
- **The side panel** opens on a row:
  - state, task, type, agent, assistant, session, "worked on for" (since it was taken),
    Blocks and Blocked by with their states;
  - links to the agent, the issue or the calls.
  - "Latest step" is left out: Connexity does not record the assistant's steps
    (rule 14).
- **"N done"**, one collapsed line, opening into the last 7 days' rows.
- **Empty states:** "Nothing waits. Your assistant is up to date." when the list is
  empty.

### The sidebar and landing

- **Work is the first item,** with a small warm count of what waits for the person, the
  same number as the page (`work.md` open question 9).
- **Landing:**
  - `/` keeps the Readiness screen until the workspace's first scan is done, then opens
    Work;
  - 10.129 turns onboarding into Work's rows and makes Work the landing from sign-up
    (question 1).
- **Action items stays** until 10.128 moves its questions onto Work. Then it is
  deleted.
- **No Dashboard:** there is no Home page to rename yet (rule 14).

## Decisions

- **The page as designed,** with Work first in the sidebar: `work.md` decisions 1 to 4,

- Everything under "Questions" is Proposed until Dmytro answers.

## Questions

1. **Landing.** Decision 20 says people land on Work, because onboarding lives there,
   and onboarding as Work's rows is 10.129. Recommend `/` showing Readiness until the
   first scan is done, then Work, and 10.129 making Work the landing for everyone. The
   alternative is Work as the landing now, with today's onboarding steps as plain rows.
2. **Reordering.** Decision 23 lets the person reorder every task except one in
   progress. That needs a stored order per workspace, which the sorting and
   `get_next_task` then follow. Recommend building it as its own roadmap row after this
   one, so this page ships first. Until then there is no drag handle and no "you can
   reorder" line. The alternative is building it here, which makes this a bigger pull
   request.
3. **What "done" lists.** Recommend the last 7 days from what Connexity already records:
   - tasks assistants finished, by assistant and session;
   - answers added to a spec, by the person;
   - specs written, by the person and assistant;
   - the first scan, by Connexity;
   - issues resolved or archived, by the person.

   The line reads "23 done this week".
4. **"Answer questions →" until 10.128.** Recommend linking to Action items filtered to
   the agent, which works end to end today. The design's cards under the row come with
   10.128.
5. **"Give before asking" on Work** (`work.md` open question 11). Work puts a task
   waiting for the person at the top of In progress, as decision 9 says. Recommend
   decision 9 winning on Work: the waiting row is the assistant's task in progress
   that needs the person, not a request opening the page. `frontend/CLAUDE.md` is
   updated to say so.
6. **MCP, `list_tasks`.** `get_next_task` ends the caller's current task, so an assistant
   cannot use it just to tell the person what is on the list. Recommend a read-only
   `list_tasks(workspace_id, cursor, limit)` answering the same list as the page,
   paginated. The alternative is no new tool.

## Risks

- **A heavy page.** It works out the whole list, the Issues page included, on every load.
  That is fine at demo size. One query per section keeps the rest cheap.
- **Sales use.** The page must look finished. Every state it can show is in the design,
  and nothing undesigned appears.
