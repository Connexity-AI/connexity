## Goal

The assistant can write each agent's spec through MCP and read it back. When the agent
moves to a new version, Connexity copies the previous spec to it and tells the assistant
to review it. The web API answers the same spec for the Spec tab in part 3.

This is what the demo needs before clarifications (10.12). The assistant writes the
demo agent's spec from its prompt, and tells the person that changing an existing
appointment is not settled.

## What exists after part 1

- **`spec`:** versions per agent, each pointing at the agent version it was written for.
  It records whether it was written or adopted, the version it follows, and who wrote it.
- **`spec_rule`:** one plain sentence, its category, its source and quote, what it
  `touches`, and a key that stays the same across versions. Rules are never edited.
- **The spec guide** is written and held back (`NOT_YET_SERVED`) until these tools
  exist.
- **Each agent version's prompt** is in the catalogue. The agent version's row links to
  its prompt or conversation flow version, which holds the content with secrets masked.
- **Each call records its agent version** (`call_component`, kind `agent`).

## Changes

### The agent's current version

The agent's **current version** is the agent version of its most recent call (by when
the call started). An agent with no calls yet has no current version, and no spec can
be written for it (question 4).

### `write_spec(workspace_id, agent_id, rules)` (MCP)

- **Writes a new spec version** for the agent's current version. Each rule has:
  - `text`;
  - `category`: a key from `list_categories`;
  - `source`: `prompt` for now;
  - `quote`: the words of the prompt it rests on;
  - `touches`: `money`, `safety`, `compliance` or none;
  - `key`: only for a rule kept from the previous version.
- **Who wrote it:** the person and the assistant, as on decision records.
- **Refused, saying what to fix, when:**
  - a category key is unknown;
  - a rule's text is empty or over 500 characters;
  - two rules share a key, or a key is not in the previous version;
  - there are no rules, or more than 500;
  - the agent has no current version;
  - **the quote is not in the prompt** (question 3).
- **Answers** the stored spec, with counts against the previous version: rules, kept,
  added, dropped. The next steps say:
  - "If kept is 0 and the previous version had rules, you may have dropped the keys";
  - list the questions the prompt leaves unsettled to the person (until 10.12).

### `get_spec(workspace_id, agent_id, version?, include_prompt?)` (MCP)

- **The latest spec version,** or the one asked for. It has its number, the agent version
  it was written for, whether it was written or adopted, who wrote it and when.
- **The rules grouped by the fixed categories,** in their order, empty categories left
  out. Each rule has its key, text, source, quote and `touches`.
- **Whether it needs review:** the latest version was adopted, or the agent has moved to
  a version newer than the spec's.
- **With no spec yet,** it answers the agent's current version and the next step: write
  one.
- **`include_prompt` (question 1):** the current version's prompt or flow from the
  catalogue, secrets masked, so the assistant writes against exactly what Connexity
  recorded.
- **It refuses** an unknown agent, an agent in another workspace, and an unknown version.

### A new agent version adopts the previous spec

- **When it happens:** a call is stored that becomes the agent's most recent call, on
  an agent version different from the latest spec's.
- **What Connexity does:** it adds a spec version for that agent version with the same
  rules and keys, marked `adopted`, with no author.
- **Only once per agent version,** and never for an agent without a spec.
- **It happens wherever calls are stored:** the minute pull, the webhook, the first scan
  and ingest. They all go through one function, `store_trace`.
- **It never reads the prompt or decides what changed.**
- `get_spec` and `list_agents` then say it needs review. The guide says what to do:
  compare the prompts, keep what holds, write what changed, and raise the questions
  the change leaves open.

### `list_agents` and `get_readiness`

- **`list_agents`:** each agent gains `spec`, one of:
  - `none`;
  - `current`: written for its current version;
  - `needs_review`: adopted, or behind the agent's current version.

  It also gains the spec's version number.
- **`get_readiness`:** once the first scan is done, a next step names the agents
  without a spec or needing review, and points to `connexity://guides/spec`.
  - **The Readiness screen is unchanged** (question 2). A step there comes with the
    Spec tab, from the design.

### Web API (for part 3)

- **`GET /agents/{agent_id}/spec?version=`:** the same answer as `get_spec`, without the
  prompt, for the open workspace. It is read-only: there is no web route to write a
  spec, because the assistant writes it.

### Guides and docs

- The spec guide moves from `NOT_YET_SERVED` into `GUIDES`.
- `get_spec` and `write_spec` answer with `guide: connexity://guides/spec`.
- The getting-started guide gains the spec as the step after the first scan.
- `docs-internal/mcp-architecture.md` lists the tools and their routes.

## Decisions

Decided by Dmytro:

- **The assistant writes the spec; Connexity stores and versions it.** A new agent
  version adopts the previous spec, and the assistant raises clarifications for what
  changed. No model runs inside Connexity (2026-11-12, roadmap entry).
- **MCP first; the Spec tab after the demo** (roadmap entry).
- **The three sub-slices** (2026-11-14).

Proposed by Claude:

- **The current version** is that of the agent's most recent call.
- **`write_spec` writes the whole rule set,** as a new version; there is no tool to add
  or remove one rule.
- **Keys:** a key that is not in the previous version is refused, so a typo cannot
  silently start a new rule.
- **Limits:** at most 500 rules of at most 500 characters each.
- **The web API** is read-only.

## Questions

1. **Should Connexity hand the assistant the prompt?** Recommended: yes,
   `include_prompt` on `get_spec` returns the current version's prompt from the
   catalogue. The spec is then written against exactly the version Connexity recorded,
   and quotes can be checked against it. The alternative is that the assistant reads the
   prompt from Retell itself.
2. **Readiness.** Recommended: the spec is a next step in `get_readiness` now, and a
   step on the Readiness screen comes with the Spec tab (part 3), after the design.
3. **Checking quotes.** Recommended: refuse a rule whose quote is not found in the
   recorded prompt, ignoring case, spacing and punctuation. A rule then cannot claim
   words the prompt does not have. When the catalogue has no prompt for the version,
   quotes are stored as given and the answer says they were not checked.
4. **An agent with no calls yet.** Recommended: no spec until its first call is stored,
   because Connexity only knows an agent's version from its calls. The alternative is to
   read the live version from Retell when the spec is written. That is a provider read
   Connexity does not do today outside sync.

## Out of scope

- **Clarifications** (10.12): raising, answering, and an answer becoming a rule. Rules
  from a clarification are refused here until 10.12.
- **The Spec tab** and the Readiness screen step (part 3).
- **Spec drift on calls** and "In conflict" (later).

## Risks

- **"Current version" follows calls.** An agent whose prompt changed but which has
  taken no call since keeps its old spec until the next call. That is accepted for
  observing; the gate will need more.
- **Quote matching is literal after normalising.** An assistant that paraphrases will be
  refused, which is the intent, but a prompt with templated variables
  (`{{customer_name}}`) needs the quote to keep them as written.
- **Adoption runs inside call storage.** A bug there could break ingest, so it is
  guarded the way checks are: a failure is logged and the call is still stored.

## Outcome

### Deviations from the plan

- **Rebased onto `main`** after part 1 (#199) merged. There were no conflicts. Part 1's
  status line now reads Done.
- **Quotes need at least 3 words.** A shorter quote is found in almost any prompt, so it
  proves nothing. Found by `/code-review`.
- **Spec writes and adoptions are made in turn.** Both lock the agent row (the lock check
  settings use), so two at once cannot collide on a version number. Found by
  `/code-review`.
- **Rules from a clarification cannot be written yet:** `write_spec` has no `source`
  field, and every rule it writes is from the prompt. 10.12 adds the other source.
- **The assistant is recorded by its registered name,** or "your assistant" when it has
  none, as archiving does since 10.1.
- **Readiness and `list_agents` leave out agents with no calls yet.** Their version is
  not known, so there is nothing to write a spec for.
- **A refusal lists at most 20 problems,** then says how many more there are.
