# Blocks and Blocked by

- **Owner:** Dmytro
- **Slice:** Demo milestone, roadmap feature "Blocks and Blocked by" (10.126). It builds
  on "Next task for the assistant" (10.124, #211) and "Session names" (10.125, #212),
  both merged.
- **Design:** `designs/16-work.md` ("Blocks and Blocked by") and `docs-internal/work.md`
  decisions 10, 11, 18 and 24. Screen: `designs/screens/Connexity Work.dc.html`. Nothing
  is built on screen here: the lock, the "Blocked by" line and the hover are the Work
  page's (10.127).
- **MCP:**
  - `get_next_task` never hands out a blocked task;
  - every task in its answer says what it blocks and what blocks it.

## Goal

Connexity knows which work has to wait for other work, and applies it by itself;
nobody maintains it. The assistant is never handed a task it cannot finish yet. A task
that blocks others sits above them in the list, so the work goes in an order that makes
sense: answer the questions about an agent, then fix it. The answer says so in the
words Blocks and Blocked by.

## Decided

- **In the roadmap row** (Dmytro, 2026-11-16, "separate task"; "one thing can block two
  or more tasks"):
  - Connexity works the dependencies out itself;
  - one task can block several;
  - `get_next_task` skips a blocked task and takes the next one;
  - a task's answer lists what it blocks and what blocks it.
- **The words are Blocks and Blocked by** (`work.md` decision 18).
- **A task that blocks a higher task sits above it** (decision 24). 10.124 built that
  rule into the sorting with no links yet (`lift_blockers`).
- **Waiting comes from Connexity's data,** never from the assistant's own blockers
  (decision 10).

## Changes

### Which task blocks which

Worked out from the workspace every time, like the tasks themselves:

| Blocker | Blocks | Why |
|---|---|---|
| An agent's open questions (Clarifications) | every issue fix on that agent | a fix follows the spec, and the answers change it (the row's example; question 1) |
| An agent's spec to write or update (Spec) | that agent's issue fixes and calls to review | both are judged against the spec (question 2) |
| Each onboarding step | the next onboarding step | the steps go in order: assistant, voice platform, agents and calls, first scan (question 3) |
| The first scan (Onboarding) | every spec task | a spec is written from an agent with its calls in (question 3) |

- **A blocker that is itself blocked** passes it on. For example: the voice platform
  blocks the agents step, which blocks the first scan, which blocks the specs.
- **A link only exists while both tasks exist.** A task stops being blocked the moment
  its blocker's work is done.
- **The row's other examples have no source yet:** Slack before the incident channel,
  tests before the deployment gate. Their links come with those features.

### The order

- **`lift_blockers` runs with these links:** each blocker moves directly above the
  highest task it blocks. It repeats until nothing moves, so chains stay in order.
- **Example:** Front desk has a Critical issue and 3 open questions. The questions move
  to the top, above the fix, which they block.

### `get_next_task`

- **A blocked task is never handed out.** The assistant gets the first task that is
  neither waiting for the person, held by another session, nor blocked.
- **Every task in the answer gains:**
  - `blocks`: the tasks it blocks, as key and title, up to 5;
  - `blocked_by`: the tasks that block it, the same way.
  - A facts line uses the words "Blocks: The same booking is made twice + 1 more" and
    "Blocked by: Answer 3 questions about Front desk".
- **Counts gain `blocked`:** tasks that wait for another task.
- **When everything the assistant could take is blocked:** "Nothing you can take now:
  N tasks are blocked by tasks that wait for the person." Then the waiting ones follow,
  as today.
- **A rule:** "A blocked task is never handed out; it waits for the tasks under Blocked
  by. A task that blocks others sits above them."

### This also settles

- **10.124's review finding** (two unfinishable setup steps could alternate): each
  onboarding step is blocked by the one before, so only the first open step is ever
  handed out.

## Questions

1. **Questions block every fix on the agent,** not only fixes on the calls the questions
   were seen on. Recommend every fix on the agent, as the row says. Matching questions
   to issues by shared calls would miss questions raised from the prompt, which have no
   calls.
2. **A spec to write or update blocks the agent's fixes and calls to review.** Recommend
   yes: both are judged against the spec. With question 1, an agent's work goes spec,
   then questions, then fixes. The alternative is spec blocking nothing, so a Critical
   fix could start on an agent whose spec is out of date.
3. **The onboarding chain, and the first scan blocking specs.** This is what the design's
   onboarding frames show ("Blocked by: Scan recent calls"). Recommend building it as
   shown.
4. **How many to list.** Recommend up to 5 under `blocks` and `blocked_by` per task, with
   the total, to keep the answer short. The facts line names the first and "+ N more",
   as the design's row does.
5. **A Critical fix blocked by questions.** The questions move above it and wait for the
   person, so the assistant moves on to setup or other work meanwhile. Recommend that.
   The assistant's steps for the questions already say to ask the person in its chat,
   and that is the quickest way to unblock the fix.

## Done when

- **Through the MCP API** on the local database, with throwaway data:
  - an agent with a Critical issue and open questions answers the questions above the
    fix, with Blocks and Blocked by on both, and the fix is not handed out;
  - answering the questions unblocks the fix, and the next ask hands it out;
  - an agent whose spec needs writing has its fix and its calls to review blocked by the
    spec;
  - in a new workspace, only the first open onboarding step is handed out.
- **`make check` passes.**

## Out of scope

- The Work page's lock, "Blocked by" line and hover (10.127).
- Links for Slack, the incident channel, tests and the gate, until those exist.
- Reordering by the person.

## Risks

- **Too much blocked.** With every fix on an agent blocked by its questions, a workspace
  with questions on every agent hands out only setup and calls to review until the
  person answers. That is the intent (decision 24), but the answer must say clearly why
  nothing else is offered, and the waiting list carries the way out.

## Outcome

### Deviations from the plan

- **An assistant asking is connected.** When an assistant calls `get_next_task`, its list
  leaves out "Connect your AI assistant". Without this, that step blocked every other
  onboarding step whenever Readiness had not seen the assistant's tokens, and the
  assistant got nothing (a play-through finding, fixed). The person's list still has
  the step.
- **The earlier task tests** moved their open questions to a third agent, Back office.
  With links, questions on Front desk block its fix, and those tests are about hand-out,
  not links.
- **Review findings left as they are:**
  - a task a session took before a blocker appeared keeps going until that session asks
    again, then waits;
  - links are worked out by comparing every pair of tasks on each agent.
