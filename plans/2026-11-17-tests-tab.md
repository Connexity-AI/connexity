## Goal

The person opens an agent's Tests tab and sees in seconds whether the version the
assistant tested holds up:
- **the verdict;**
- **what failed,** critical first, each with how often and links to the simulated
  calls;
- **coverage:** how much of the spec the runs checked;
- **the scenarios and sets** that did the checking.

It is read only: the assistant writes scenarios and runs them through MCP.

## What exists

- **Test results (10.1293)** give a version's verdict, its totals per rule, its code
  checks with severity and the runs that count. `get_test_runs` answers them.
- **A simulated call** opens on the call screen with the rules it was judged on.
- **Scenarios and sets** are listed by `list_scenarios`. It also names the rules no
  scenario lists, critical first.
- **The agent page** has Overview, Calls and Spec. The Spec tab loads the spec on the
  server through a web route.

## Changes

### The design adjustment (question 1)

I write a Claude Design prompt in `designs/12-adjustments.md`, item 31, "Tests tab: the
demo cut". It covers:
- **The tab label:** "Tests 86%", the coverage.
- **Number tiles,** each with its base:
  - the verdict, "Version 15 Failed" (or Verified, or Not tested), with "Edited" when
    the draft was changed;
  - coverage, "114 of 132 rules";
  - scenarios, "38 in 3 sets";
  - flaky rules;
  - warnings.
- **Why it failed:**
  - failed critical rules and critical code checks first, then warnings;
  - each rule row: the rule, its Critical badge, its category and "Failed in 2 of 5
    simulated calls";
  - opening a row lists its simulated calls, each with its scenario and verdict and a
    link to the call;
  - each code check row: its title, severity and "Found in 2 of 40 simulated calls",
    with the same links.
- **All rules:** a collapsed section grouped by the fixed categories. Each rule shows
  passed, failed and didn't come up.
- **Not checked:** a collapsed section, grouped by category. These are the spec's rules
  no run judged:
  - "No scenario" when no scenario lists them;
  - "Didn't come up" when scenarios list them but never reached them.
- **Scenarios and sets:** the sets with their counts, then the scenarios. Each shows its
  name, the caller's goal in a line, the number of rules it lists and its sets.
- **Empty states, each saying what the assistant does next:**
  - no spec: "The assistant writes the spec first";
  - no scenarios: "The assistant writes scenarios" (the Work task);
  - no run yet: "The assistant runs the scenarios through MCP".
- **Not on the tab:** a Run button, version history, audio and phone rows, overrides,
  or editing a scenario.

The tab is built after you update the design, in this PR (question 2).

### Coverage (question 3)

- **A rule is covered** when the shown version's runs judged it Passed or Failed at
  least once. Didn't come up does not count.
- **Coverage counts the latest spec's rules.** A rule a newer spec dropped is not
  counted.
- **Each uncovered rule says why:** no scenario lists it, or its scenarios never
  reached it.

### "Failed in 2 of 5" (question 4)

Counted over simulated calls that judged the rule, Passed or Failed. Didn't come up is
left out.

### Backend

- **`GET /agents/{id}/tests`** (web, the person's session) answers:
  - the newest tested version's results (from 10.1293);
  - coverage;
  - for each failed rule and each code check with findings: its simulated calls, with
    scenario names and verdicts, at most 20 each;
  - the scenarios and sets.
- **The agent page** loads it for the Tests tab and its label.

### MCP

- **`get_test_runs`' results** gain `coverage`: rules checked, rules in the spec, and
  the unchecked rules with why, critical first.
- **A next step** names the critical rules not checked and points at `write_scenarios`.

## Questions

1. **The design adjustment as above.** Recommend this cut: tiles, why it failed, all
   rules, not checked, scenarios and sets. Say what to add or take out before I write
   the prompt.
2. **One PR with the screen built after your design update,** as with Critical rules and
   Test results. The alternative is backend and MCP first in one PR, and the tab in a
   second.
3. **Coverage over the shown version's runs, against the latest spec,** with Didn't
   come up not counted. The alternative is counting a rule as covered when any scenario
   lists it, whether or not a run reached it. That is simpler, but it overstates what
   was tested.
4. **"Failed in 2 of 5 simulated calls"** counts only calls that judged the rule. The
   alternative counts runs ("in 1 of 2 runs"), which hides how often a rule fails
   within a run's repeats.
5. **The tab always shows** once built, with the empty states above, so the person can
   see where testing stands for every agent. The alternative is showing the tab only
   when the agent has scenarios.

## Outcome

### Deviations from the plan

- **Built on the test results branch** (#222, merged since).
- **The tab follows design item 31,** updated in
  `designs/screens/Connexity Agent Profile.dc.html`. Where it differs from the plan:
  - "All rules" lists only the rules the runs judged (Passed or Failed at least once).
    The others are under "Not checked".
  - "All rules" and "Not checked" show only after a run.
  - A code check's simulated calls read "Failed" when the check fails calls and
    "Flagged" when it only flags them.
  - The flaky tile reads "of N checked".
- **The agent page loads the Tests tab on every tab,** because the tab's label shows
  coverage.
- **`tested_version` is named `version_tested`:** pytest collected the old name as a
  test, because the file is `services/test_run.py`.
- **Review findings:** both left as they are.
  - Loading the tab on every tab is small at demo scale (skipped).
  - A failing rule's Critical badge comes from the spec version its run judged, as
    the verdict does (no change needed).
