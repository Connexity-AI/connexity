## Goal

After this merges, Connexity has a place to keep every agent's spec, version by version,
and a written guide for how the assistant writes one. Part 2 builds the tools on both
without reopening either. The schema and the guide are settled first because a wrong
shape or a wrong rule for writing specs would be expensive to change once specs exist.

From the roadmap (the whole epic): "The assistant writes each agent's spec from its
prompt through MCP, guided by Connexity's spec guide; Connexity stores it. Specs are
versioned. A new agent version always adopts the previous spec, and the assistant raises
clarifications for whatever the prompt change touched (Connexity takes this over later).
The spec guide tells the assistant to raise a clarification for behaviour seen on calls
that the prompt does not settle (demo step 4 depends on this). Rules grouped by the
fixed categories, with their source. MCP first; the read-only Spec tab can follow after
the demo. No model runs inside Connexity; spec drift detection on calls comes later."

## What exists today

- **Nothing about specs:** no table, route, tool, guide or Readiness step.
- **Connexity knows each agent's versions and their prompts:**
  - each call records the Retell agent version that served it (`call_component`, kind
    `agent`);
  - the catalogue (`component_version`) keeps each version's prompt or flow with its
    content and a fingerprint.
- **The 14 fixed categories** are a table (10.02).
- **Decision records** already say who decided what. Since 10.1 they also name the
  assistant that acted, with the person who approved.
- **The MCP guides** live in `mcp_server/src/connexity_mcp_server/guides/`, one Markdown
  file each, served as `connexity://guides/<name>`.

## Changes

### Schema (models, one migration)

**`spec`:** one row per version of an agent's spec.

| Field | What it holds |
|---|---|
| `id`, `company_id`, `agent_id` | As every tenant row; deleting the agent deletes its specs |
| `version` | 1, 2, 3 … per agent; unique with `agent_id` |
| `agent_version` | The Retell agent version it was written for, as calls record it ("14") |
| `prompt_fingerprint` | The fingerprint of that version's prompt or flow in the catalogue, if known |
| `origin` | `written` (by the assistant or a person) or `adopted` (copied when the agent version changed) |
| `previous_id` | The spec version it follows; none for the first |
| `created_by`, `created_by_email`, `assistant_name` | Who wrote it, as on decision records; none for an adopted copy, which Connexity makes |
| `created_at` | When |

The latest version (highest `version`) is the agent's spec. Older ones are history and
never change.

**`spec_rule`:** the rules of one spec version.

| Field | What it holds |
|---|---|
| `id`, `company_id`, `spec_id` | Deleting a spec version deletes its rules |
| `key` | A stable id for the rule across versions: kept rules carry it from version to version, so versions can be compared (kept, added, dropped) |
| `position` | Its order within its category |
| `category_id` | One of the fixed categories; a category in use cannot be deleted |
| `text` | The rule in one plain sentence |
| `source` | `prompt` or `clarification` |
| `quote` | For a rule from the prompt, the prompt's words it rests on |
| `clarification_id` | For a rule from a clarification; a plain id until 10.12 adds the table |
| `touches` | `money`, `safety`, `compliance` or none |

`key` is unique within one spec version.

**Rules are never edited.** Any change is a new spec version with its own rows, so every
version stays exactly as it was written.

### The spec guide

A new file, `guides/spec.md`, reviewed in this pull request and served in part 2. Its
outline:

1. **What a spec is:** what the agent is supposed to do, as plain rules, one version per
   change. Connexity uses it to tell real behaviour from what was intended. Tests come
   from it later.
2. **When to write one:** after the first scan, for every added agent without a spec;
   and again when Connexity says the agent moved to a new version.
3. **How to write a rule:**
   - one behaviour, one plain sentence, in the business's words ("Never book a slot
     outside opening hours");
   - only what the prompt settles. Quote the words it rests on, and never infer a rule
     the prompt does not state;
   - one of the fixed categories (`list_categories`). Technical categories rarely hold
     rules;
   - mark rules that touch money, safety or compliance;
   - no rules about tone or wording unless the prompt makes them a requirement.
4. **What is not a rule: a question for the person.** Behaviour seen on calls that the
   prompt does not settle is raised as a clarification, never written as a rule, and
   never answered by the assistant alone. Example: the agent changes existing
   appointments on 7 of 78 calls, and the prompt says nothing about changing one. Until
   clarifications ship (10.12), list these questions to the person.
5. **A new agent version:**
   - Connexity copies the previous spec to the new version;
   - compare the two prompts;
   - keep the rules that still hold, with their keys;
   - rewrite or drop what changed;
   - raise a clarification for anything the change leaves unsettled.
6. **Keys:** pass back each kept rule's key, or it reads as dropped and added again.
7. **What Connexity does and does not do:** it stores, versions and checks the shape. It
   does not read prompts with a model, and it never writes rules itself.

## Decisions

Decided by Dmytro:

- **The epic is three pull requests:** schema and guide, then API and MCP, then frontend
  (2026-11-14).
- **The assistant writes the spec as a Readiness step,** not on connection. An agent can
  be without one (2026-11-12).
- **Specs are versioned.** A new agent version adopts the previous spec, and the
  assistant raises clarifications for what changed (2026-11-12, roadmap entry).
- **Rules use the fixed categories and show their source** (2026-11-12, prompts 03 to
  06).
- **No model inside Connexity; spec drift detection on calls comes later** (roadmap
  entry).

Proposed by Claude:

- **Spec versions are numbered per agent,** each pointing at the agent version it was
  written for. One agent version can have several spec versions (a rewrite, then an
  answered clarification); the latest counts.
- **Rules are never edited in place;** stable keys let versions be compared.
- **`touches`** (money, safety, compliance) is a field now, set by the assistant, so the
  Spec tab can mark such rules later.
- **No MCP change in this part.** The guide names `write_spec` and `get_spec`, so serving
  it before they exist would send the assistant to tools it cannot call. It is served in
  part 2. Rule 10 is met by part 2, which ships the tools for this schema.

## Questions

1. **The guide's stance on tone and wording.** Recommended: no rules about how the agent
   sounds unless the prompt makes it a requirement ("always say the clinic's name"),
   because style rules are many, vague and untestable. The alternative is to capture
   them too, as low-weight rules.
2. **Where the guide's best practices come from.** The vision says you will write out
   Connexity's framework for building agents. Recommended: this outline is the first
   version; you review its wording in this pull request, and your framework replaces or
   extends it later. The alternative is to wait for your text.

## Outcome

### Deviations from the plan

- **The schema tests live in `app/tests/crud/`, not `app/tests/models/`,** because the
  models folder runs without a database and these rules are enforced by Postgres.
- **The guide is guarded by a test.** `guides.py` has a `NOT_YET_SERVED` list, holding
  `spec`, and a new MCP server test fails if any file in `guides/` is neither served nor
  on that list. Part 2 moves `spec` into `GUIDES` when it adds the tools. Found by
  `/code-review`.
- **The guide's example uses invented numbers** ("9 of 120 calls"), not the demo
  workspace's, because the repo is public.
- **Deleting a spec version keeps the next one** and clears its link to the deleted one
  (`previous_id` set to null). The plan did not say; a test covers it.
