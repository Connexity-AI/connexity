# Next task for the assistant

- **Owner:** Dmytro
- **Slice:** Demo milestone, roadmap feature "Next task for the assistant" (10.124).
- **Design:** `designs/16-work.md` and `docs-internal/work.md` (the Work page, #209);
  screen `designs/screens/Connexity Work.dc.html`. The screen is not built here: this
  feature is MCP only (roadmap row), and Work is 10.127. `designs/15-assistant-tasks.md`
  is committed with this pull request, marked superseded by `16-work.md`.
- **MCP:**
  - adds `get_next_task`;
  - the server instructions and every tool's next steps point at it.

## Goal

The assistant does not have to work out what matters. At the start of a session and
after each task, it asks Connexity, and gets the single most important thing to do in
this workspace. The answer says what it is, the rules that apply, numbered steps and the
tools to use, and how many tasks wait. In the demo, steps 4 to 6 flow from
"what's next?" (roadmap row).

## Decided in the roadmap row

These are Dmytro's words, 2026-11-15:
- **Per workspace only.** Nothing about other workspaces appears in the answer.
- **Tasks are worked out from the current state,** so a task disappears when its work
  is done.
- **Connexity does the sorting; the assistant just gets the next task** (Dmytro,
  2026-11-16).
- **The order** (Dmytro, 2026-11-16, replacing the row's two lanes): incidents always
  first, then Critical tasks, then setup tasks in Connexity's order, then all other
  issues and clarifications. A task that blocks a higher task sits above it.
- **Every task can be reordered except one In progress** (Dmytro, 2026-11-16, replacing
  "operational tasks can't be reordered"). Reordering is not built here.
- **All issues are tasks, Critical on top** (Dmytro, 2026-11-16, widening the row's
  "critical issues").
- **`get_readiness` stays the number;** its open steps become setup tasks.
- **Tasks that end with a person's decision** go to the person in the chat, and show on
  Work as waiting for you (Action items folds into Work, 2026-11-16).
- **A task an assistant took is In progress,** and other assistants skip it. A task stuck
  In progress is acceptable for now.
- **Waiting comes from Connexity's own data,** not from the assistant reporting it; no
  session blockers are tracked (`work.md` decision 10, 2026-11-16).
- **Session names and Blocks / Blocked by are their own rows** (10.125, 10.126), not
  this feature (2026-11-16).

## Changes

### The tasks Connexity can work out today

| Kind | One task per | Exists when | Done when |
|---|---|---|---|
| Incident | — | not built yet (Milestone 5); none (question 1) | — |
| Issue fix | issue | an open or reopened issue | it is resolved or archived |
| Onboarding | step | a Readiness step that is not done | it is done |
| Spec | agent | the agent's spec is missing or needs review (`agents_needing_specs`) | the spec is current |
| Clarifications | agent | the agent has open questions | none are open |
| Calls to review | agent | calls Connexity could not check (`unchecked`) in the last 7 days (question 2) | none are left |
| Tests | — | not built yet (10.17); none | — |

### The order

Connexity sorts one list per workspace, every time it is asked. The assistant only ever
gets the top task it may take.

1. **Incidents,** always first. None exist yet.
2. **Critical tasks:** Critical issue fixes, the issue on more calls in the last 30 days
   first, then the most recently seen.
3. **Setup tasks, in Connexity's order:** open Readiness steps (Onboarding) in
   Readiness's order, then specs, missing before needs review (question 12).
4. **All other tasks:** the remaining issue fixes (warnings, and reopened ones that are
   not Critical), clarifications and calls to review, sorted together by calls: calls
   affected for an issue, calls the questions were seen on for clarifications, unchecked
   calls for calls to review. More calls first (question 13).
5. **Ties:** the oldest task first, so the order stays the same between asks.

**Blocks.** A task that blocks a higher task moves directly above the highest task it
blocks. Which task blocks which is 10.126; until it is built nothing blocks, and the
rule is written into the sorting so 10.126 only adds the links (question 14).

**Reordering.** Every task except one In progress can be moved by the person. That is
not built here. When it is, the person's order wins over the one above.

### `get_next_task(workspace_id)`

- **The single next task,** skipping those another assistant has In progress. It is
  marked In progress for the calling assistant (question 3).
- **Asking again ends the caller's current task** (Dmytro, 2026-11-16: "Next means my
  part is done"):
  - done when its work is gone;
  - waiting for the person when the rest is theirs (an issue fix: they resolve it once
    the fix is live);
  - a review of calls is done once handed out;
  - otherwise it goes back to its place in the list, and is never handed straight back
    to the same assistant.
- **The task answers:**
  - its kind, its place in the list and its key (`spec:<agent id>`);
  - one plain line: "Write the spec for Front desk";
  - the agent;
  - the facts (counts, versions, the issue's size);
  - the rules that apply;
  - numbered steps naming the tools (`get_spec` with include_prompt, `write_spec`,
    then `raise_clarifications`);
  - the guide.
- **Counts:** how many tasks are to do, how many wait for the person, and how many are
  In progress with other assistants.
- **With nothing to do:** "Nothing waits in this workspace", with Readiness's percentage.

### When the work needs the person

- **Waiting is worked out from the data, not reported** (decision 10). A task whose
  next move is the person's is waiting for the person. Today that is an agent with open
  clarifications: only the person answers them.
- **A waiting task is never taken or marked In progress** (question 4). The answer lists
  the waiting tasks apart from the assistant's own task, with the steps "ask the person
  in your chat; call `answer_clarifications` with what they pick; otherwise leave it,
  they can answer in Connexity".
- **The assistant's own task** is the first task that is not waiting. So the assistant
  raises them with the person, then gets on with its own work.
- **Waiting tasks are counted in the answer** ("2 wait for the person"). On screen they
  show on Work (10.127); until then, open clarifications show on Action items.

### In progress

- **A new table, `assistant_task`:**
  - workspace;
  - the task key, its kind and its one-line title, and its agent;
  - the person and the assistant (name) that took it;
  - its state: in progress, waiting (the assistant's part is done, the rest is the
    person's), returned or done;
  - when it was taken, when the assistant's part ended, and when it was done.
  Questions and the person's own setup step wait by their data and are never taken
  (question 4).
- **Rows are kept.** A task that no longer exists is no longer In progress; its row is
  marked done, never deleted, with when it was done (question 8). No timers (roadmap
  row).
- **Assistants are told apart** by the person and the assistant name Connexity already
  records on decisions (question 3).

### Pointing the assistant at it

- **Server instructions** gain: "At the start of a session and after each task, call
  `get_next_task`."
- **Every tool's last next step,** where a task can be finished by that tool, becomes
  "When this task is done, call `get_next_task`." These tools are `write_spec`,
  `answer_clarifications`, `raise_clarifications`, `archive_issue` and `scan_calls`.
- **`get_readiness`'s next steps** gain the same line.
- **The getting-started guide** gains a short "What to do next" section.

## Questions

1. **Kinds with no source yet.** Incidents (Milestone 5) and tests (10.17) do not
   exist. Recommend no placeholder tasks for them. They join when
   their features are built.
2. **"Calls to review".** Recommend calls in the last 7 days that no check could run on
   (`unchecked`), one task per agent. The steps: open a few with `get_call`, say to the
   person why they could not be checked (for example no tool calls or a missing
   recording), and raise anything the spec does not settle. Say if you meant something
   else.
3. **Who "an assistant" is, until Session names (10.125).** Recommend the person plus
   the assistant's name, as decisions record it. Two Claude Code sessions of the same
   person then count as one assistant and share the task, until 10.125 keys them by
   session.
4. **Waiting for the person.** Decision 10 rules out the assistant reporting that it
   waits. Recommend that a waiting task is never taken: `get_next_task` lists the
   waiting tasks for the assistant to raise in its chat, and hands it the first task
   that is not waiting. So clarifications keep their place in the list as "wait for the
   person", and the assistant's own task is the next one below them.
   This drops the `waiting_for_person` argument and the 24-hour fallback of the first
   draft.
5. **One task per agent** for clarifications, specs and calls to review, and one per
   issue and per Readiness step. Recommend yes: "Answer 3 clarifications on Front desk"
   is one sitting.
6. **Settled by the new order:** Readiness steps are setup tasks, not a roadmap lane.
7. **`designs/15-assistant-tasks.md`** is committed with a line at the top saying it is
   superseded by `16-work.md` (Dmytro, 2026-11-16). Nothing to decide.
8. **Done tasks are kept** (Dmytro: "They are not deleted"; Work's done section,
   design 16). Done rows on Work come from three places: "Spec written for Car service
   booking · version 1 · Alex's Claude Code", "3 answers added · Alex" and "First scan:
   5 issues found · Connexity". So a done task is not only one an assistant took.
   Recommend:
   - here, `assistant_task` rows are marked done, never deleted;
   - Work's done list (10.127) is built from what Connexity already records: spec
     versions with their author, answers, scans, and resolved or archived issues. Each
     names who did it.
   Nothing in this feature shows done tasks.
9. **Dropped.** It was about how the code is built, not a decision: Connexity sorts the
   one list, `get_next_task` hands out its top task, and Work (10.127) will show that
   same list.
10. **Kind names** are the design's types (Dmytro: "agree"): Clarifications, Spec, Calls
    to review, Issue fix, Incident, Tests, Onboarding.
11. **Settled:** all issues are tasks, Critical on top (Dmytro).
12. **Specs are setup tasks.** The Work design lists "Write the spec for each agent" as
    an onboarding step, and a fix needs the spec. Recommend specs in group 3, after the
    open Readiness steps.
13. **One measure for "all other": calls.** Recommend sorting issues, clarifications
    and calls to review together by how many calls they touch. The alternative is a
    fixed order of kinds inside the group (issues, then clarifications, then calls to
    review).
14. **Blocks now or with 10.126.** The clearest case is an agent's open questions
    blocking its Critical fix: the questions should sit above the fix. Recommend leaving
    every link to 10.126 and building only the rule now. The alternative is adding that
    one link here.

## Risks

- **A wrong order** sends the assistant to the wrong work first. The order is written down
  in the rules of every answer, and the person can change it once reordering is built.
- **Shared identity** (question 3): two sessions of one person's assistant may get the
  same task.

## Outcome

### Deviations from the plan

- **Moving on** (decided while building, Dmytro, 2026-11-16: "Next means my part is
  done"). The plan handed the same task back as "still in progress". But an issue fix
  and a review of calls never show done in the data by the assistant's work alone, so
  the assistant would have been stuck. Asking again now ends the current task:
  - done when its work is gone;
  - waiting for the person for an issue fix;
  - done once handed out for a review;
  - otherwise returned to its place, never straight back to the same assistant.
- **`assistant_task` has states** (in progress, waiting, returned, done) and keeps
  `ended_at` and `done_at`, to carry the above.
- **A review of calls** counts the agent's unchecked calls since its calls were last
  handed out for review, within 7 days. Without that, the same calls would come back
  every time.
- **`work.md`:**
  - decision 6 is struck through and replaced by 23 to 25 (reordering, the order, all
    issues);
  - open question 6 (regular issues) is settled;
  - `REBUILD.md` logs the same.
- **Review findings, all left as they are:**
  - **Setup steps can alternate:** two setup steps the assistant cannot finish alone can
    alternate when it keeps asking. Blocks (10.126) orders them.
  - **Unchecked calls are counted in Python.**
  - **The Issues page is recomputed** on every ask.
  - **"Connect your AI assistant" looked waiting** in the play-through, only because
    its tokens were minted for testing (no change needed).
