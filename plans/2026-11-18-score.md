# Score

- **Owner:** Dmytro
- **Slice:** Demo milestone, roadmap feature "Score" (10.19).
- **Design:** No UI change: the Dashboard (10.191) shows it. Design prompts for the rules:
  `01-system-home-roadmap.md` (score), `12-adjustments.md` (archiving, Readiness).
- **MCP:** `get_agent` answers the agent's score; `list_agents` answers the workspace's. No new tool; the contract page lines for both change.

## Goal

Every agent and every workspace has a score from 0 to 100 for a period, with its change,
and the assistant can see what moves it. A basic formula now, kept in one place so a
better one can replace it.

## Decisions

- **Accept, build** (Dmytro, 2026-11-18).
- **Score = 100 × (1 − (failed + 0.5 × degraded) / checked calls) over the period, per
  agent and per workspace, with its change over the period** (Dmytro, 2026-11-18: "we can
  do very basic score formula for now to not hardcode it and later devise something
  better"; "formula ok").
- **The formula lives in one place,** to be swapped later (Dmytro, 2026-11-18).
- **No milestones for now** (parked with the roadmap, Dmytro 2026-11-18).
- **Shown only when onboarding is complete** (Dmytro, 2026-11-18).
- **Only fixes and improvements raise it,** never answering questions or setting things
  up; **Readiness never changes it** (2026-11-09, 2026-11-12).
- **MCP returns the score with what moves it** (Dmytro, 2026-11-18).
- **Archived issues are hidden on every call, as call results already do** (Dmytro,
  2026-11-18, question 1, keeping the 2026-11-14 decision over the roadmap row's "from the
  day they are archived"): archiving lifts the score for the whole period.
- **The change is against the previous period of the same length** (Dmytro, 2026-11-18,
  question 2).
- **The assistant reads it in `get_agent` and `list_agents`;** no new tool (Dmytro,
  2026-11-18, question 3).

## What exists

- **A call's result** (`call_check_statuses`): failed when a finding fails the call,
  degraded when findings only flag it, clean when checks ran and found nothing,
  unchecked otherwise. Findings of archived issues are left out on every call
  (2026-11-14).
- **The Calls page's tiles** count calls by result for a period and an agent
  (`workspace_calls`): the formula's inputs already exist.
- **Readiness** says when the four Getting started steps are done; the onboarding list
  (10.18) holds them in order.

## Changes

### The score

- **`app/services/score.py`, one function:** given the failed, degraded and checked
  counts, the score, rounded to a whole number. The only place the formula lives.
- **Checked calls** are calls with a result other than unchecked. **No checked call in
  the period:** no score ("not enough calls yet"), never 100 by default.
- **Per agent and per workspace,** for 7, 30 (default) or 90 days, from the same counts
  as the Calls page.
- **Its change** against the previous period of the same length: this
  period's score minus the last one's, none when either has no checked call.
- **What moves it:** the issues that cost the most points in the period, worst first,
  each with its points: how much the score would rise if that issue's findings were
  gone (each affected call recounted without it). Up to five, with their ids, for the
  assistant to fix.
- **Archived issues** count as call results count them: hidden on every call while
  archived, counting again once unarchived.

### Onboarding complete

- **The score is shown only once onboarding is complete:** every Readiness step done.
  Before that, the answer says "Score comes after onboarding" and what is left. When
  10.192 adds steps to the onboarding list, complete follows them.

### MCP

- **`get_agent`:** the agent's score, change, checked calls and what moves it.
- **`list_agents`:** the workspace's score and change, and each agent's score.
- **Rules:** the score is 100 × (1 − (failed + 0.5 × degraded) / checked calls); only
  fixes raise it; say the base ("78 over 412 checked calls in 30 days").
- **Contract page:** the two tools' lines updated (CLAUDE.md rule 10).

### Docs

- `docs-internal/metrics.md`: the score, its formula, what counts, and that it is basic
  and will be replaced.

## Done when

- Through the API on the local database, with invented calls:
  - an agent with 10 checked calls, 2 failed and 2 degraded scores 70; its change against
    a previous period at 80 is −10;
  - no checked call: no score;
  - "what moves it" names the issue that costs the most points first, with its points;
  - archiving an issue lifts the score for the whole period; unarchiving lowers it back;
  - before onboarding is complete, no score and what is left.
- `make check` passes.

## Out of scope

- Showing the score on a screen (10.191, Dashboard).
- Milestones and score history.
- A better formula.

## Risks

- **Turning a check off or to "flags" raises later calls' score.** That is a setting, not
  a fix. It is recorded as a decision and never rewrites past calls, but it still lifts
  the number for new calls. Reviewer: acceptable for a basic score?

## Outcome

### Deviations from the plan

- **The workspace's score is on each `list_workspaces` row** (score and change over 30
  days), not on `list_agents`: `list_agents` answers a list, and putting the workspace's
  score beside it broke the standard answer shape (`data`, `rules`, `next_steps`,
  `guide`, `next_cursor`, which a test enforces), while turning `data` into an object
  would break a running MCP server mid-rollout (the lesson of PR #231). `list_agents`
  still answers each agent's score. This moves part of question 3's answer ("get_agent +
  list_agents") to `list_workspaces`; confirmed by Dmytro, 2026-11-18 ("Yes, push").
- **`get_agent`'s score is on the MCP answer only** (`McpAgentPage`); the web app's agent
  page is unchanged until the Dashboard (10.191).
- **Halves round up** (82.5 shows 83), not Python's round-to-even.
- **`get_agent` adds a next step** naming the issue that costs the score most, with its
  points and its `get_issue` call.
