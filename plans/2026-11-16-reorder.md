# Reorder tasks on Work

- **Owner:** Dmytro
- **Slice:** Demo milestone, roadmap feature "Reorder tasks on Work" (10.1271), split out
  of the Work page (10.127, #214) on 2026-11-16. #214 has merged.
- **Design:** `designs/16-work.md` ("To do rows show a drag handle there on hover"; the
  line "You can reorder what hasn't started") and `docs-internal/work.md` decisions 5, 6,
  23 and 24. Screen: `designs/screens/Connexity Work.dc.html`. Its rows drag within To
  do. Prompt 15's "Move to" menu is superseded and not built.
- **MCP:** `move_task`, for when the person asks their assistant to change the order
  (question 4).

## Goal

The person sets what comes next. They drag a task in To do to where they want it, and
from then on the assistant gets tasks in that order. Connexity's order stays the default
for everything the person has not moved, and for new tasks as they appear.

## Decided

- **Every task can be reordered except one in progress** (decision 23). Tasks waiting
  for the person sit in In progress, so they are not moved either.
- **Assistants pull; Connexity and the person set the priority** (decision 5).
- **Incidents always first** (Dmytro, 2026-11-16, decision 24): question 1.
- **A task that blocks a higher task sits above it** (decision 24): question 2.
- **Drag on To do rows,** as the design shows.

## Changes

### Storing the person's order

- **A new table, `task_order`:**
  - workspace;
  - the task keys in the order the person last left To do, as a list;
  - who moved it and when.
  One row per workspace. Each move replaces the list.
- **Merging with Connexity's order,** each time the list is worked out:
  1. Tasks in the person's list keep their order among themselves.
  2. A task not in it (new since the move) takes its place by Connexity's order: just
     before the first listed task that Connexity ranks below it.
  3. Tasks that no longer exist drop out.
  4. Then the Blocks rule runs, so a blocker still sits directly above what it blocks.
  5. Incidents stay first (question 1).
- **`get_next_task`, `list_tasks` and Work** all follow the merged order, because they
  share `work_list`.

### Moving

- **`POST /work/order`** (web): the task moved, and the task it now sits before (none
  means the end).
  - It refuses a task that is in progress or waiting, and an unknown key.
  - It answers the new page.
  - Each move is a decision record ("task order", who and when), as other decisions
    are.
- **MCP `move_task(workspace_id, key, before)`:** the same, recorded with the assistant
  that acted.

### The page

- **To do rows show a drag handle** in the marker column on hover, as designed, and drag
  within To do. A blocked row keeps its lock, and shows the handle on hover.
- **The line under "Assistant tasks"** becomes the design's: "Your assistant works down
  this list from the top. You can reorder what hasn't started."
- **The move shows at once,** then the page refreshes from the answer. When the move is
  refused, the row goes back and a short line says why.
- **No keyboard reordering** (question 3, Dmytro: "no need any keyboards").

## Decisions

- Everything under "Decided" is Decided.
- Everything under "Questions" is Proposed until Dmytro answers.

## Questions

1. **Incidents and reordering.** Decision 23 lets every task but one in progress move.
   Decision 24 puts incidents always first. Recommend that incidents stay first and show
   no handle. None exist yet (Milestone 5), so today this changes nothing.
2. **Moving a task above what blocks it.** If the person drags a fix above the questions
   that block it, the Blocks rule moves those questions up with it, directly above the
   fix. Recommend that: it keeps "blockers sit above" true, and answers "do this fix
   first" by bringing up what it needs. The alternative is leaving the fix above its
   blockers, still not handed out until they are done.
3. **Keyboard reordering.** Decided: none. Dmytro, 2026-11-16: "no need any keyboards".
   Reordering is by drag only, as designed.
4. **`move_task` through MCP.** Recommend it, with the rule "only when the person asks;
   never to reorder on your own", recorded with the assistant that acted. Then "do Night
   line first" works from the assistant's chat too (rule 10).
5. **Going back to Connexity's order.** The design has no reset. Recommend none for now:
   the person drags back. A "Reset order" link would start in the design.

## Out of scope

- Moving tasks in progress or waiting, and incidents (question 1).
- Keyboard reordering (question 3).
- A reset to Connexity's order (question 5).
- Goals and the zoomed-out roadmap (decision 22).

## Risks

- **The person's order goes stale** as tasks come and go. New tasks fall in by
  Connexity's order around the person's, so nothing is lost. A long-forgotten order
  still wins over Connexity's for the tasks it lists; question 5 is the way out if that
  bites.
- **Two people reorder at once.** The last move wins; each is recorded.

## Outcome

### Deviations from the plan

- **Moves are not decision records.** A decision record needs an agent, and a move has
  none. The order itself keeps the last move instead: the task, who moved it, the
  assistant that acted, and when. Earlier moves are not kept.
- **Moving a task before itself is refused.** So are moves of an unknown key and of a
  task not in To do.
- **The first frontend build failed** on a Google Fonts fetch and passed on a rerun.
- **Review findings left as they are:**
  - dropping a row above its blocker shows it there, then the refresh lifts the blocker
    above it, so the list jumps once;
  - the test of a task appearing after a move does not pin its exact place;
  - only the last move is kept (above).
