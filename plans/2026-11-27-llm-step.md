# The LLM step: confirm spec flags, judge LLM rules

- **Owner:** Dmytro
- **Slice:** Roadmap 105.16, "LLM approval step for spec findings". It builds on 105.14
  (each rule's check type and inputs) and 105.15 (the spec check).
- **Design:** `designs/26-llm-step.md`. A spec finding from the LLM step can have a
  moment and a reason, and the call screen shows every spec finding as having none
  today.
- **MCP:** `get_call` and `get_issue` give a confirmed finding's moment, reason and the
  model that confirmed it. `get_spec` and the spec guide say that both types are now
  judged. The contract entries are updated.

## Goal

Two of the three check types from 105.14 do nothing yet: `classifier_then_llm` flags are
held, and `llm` rules are not asked. This step is an LLM that:

- reads a call flagged on a `classifier_then_llm` rule, with that rule, and confirms or
  dismisses the flag;
- judges each `llm` rule on every judged call directly;
- gives the moment in the call and the reason when the rule was broken.

It is the only step given long inputs, such as the call history (105.14).

Why it is needed (the 2026-11-26 lab): the classifier raises conditional rules and
unusual calls well but cannot settle them, and its probability does not tell those
flags apart. The unclear flags were all at 0.9 or above.

This row builds the system. How good its prompt and model are for each kind of rule is
lab work afterwards (decision 1).

What the hosted database holds today (counts only):

- The two agents with a spec have 103 rules, all `classifier`, 23 critical. None names an
  input.
- The spec check is merged but has not run there yet: no runs, no findings.

So the step has nothing to judge until the assistant retypes rules under the guide.
Its cost grows with the number of `llm` rules.

## Changes

**The step, inside the spec check.** It is version 2 of `spec_rule_broken`, not a new
check: the same issue per rule, the same settings, one stored answer per call.

1. The classifier asks as in 105.15.
2. Then the LLM is asked, **one rule per request** (decisions 2 and 3):
   - for each `classifier_then_llm` rule the classifier scored at 0.8 or above;
   - for each `llm` rule.
   A call's requests go out together.
3. Its verdict per rule is broken, kept, or did not come up, written after its reason
   and the lines it rests on. This is the shape the test-run judge uses
   (`services/rule_judge.py`). There, a verdict given before its reason was
   contradicted by that reason in 4 of 14 failures.

**What one request holds.** Only what its rule names, as in 105.14:

- the whole call as numbered lines, with tool calls and their results and secrets
  masked (the classifier's `render`);
- the inputs the rule names, long ones included;
- last, the one rule's text and its clarifications in force. Putting the rule last
  means a call's requests start the same way, which providers that discount a repeated
  start charge less for.

Never in it: the agent's prompt (decision 5), any other rule, or the classifier's
score. The LLM judges the rule afresh, so the score does not lead it.

**The model.** Claude Haiku 5.5 to start (decision 4).

- It is set by `SPEC_LLM_MODEL`, asked through the judge helper model checks already
  have (`checks/judge.py`), which prices it for the daily budget. The test-run judge
  already runs on the same model (`SIMULATION_MODEL`).
- Each stored answer names the model that gave it.
- Changing the setting judges new calls with the new model and leaves judged calls as
  they are, as for any other change to the check.

**What it answers.**

- **Broken:** a finding with the moment (the event ids the reason rests on) and the
  reason.
  - Ids not in the call are dropped. If none are left, the finding is on the whole
    call, as in 105.15.
  - For a confirmed flag, its detail names the classifier and its probability, and the
    LLM that confirmed it.
- **Kept or did not come up:** no finding. The verdict and the reason are stored with
  the answer and shown nowhere until 105.17 (marking false positives) reads them.
- **Who found it:**
  - A confirmed flag is "found by the classifier, confirmed by" the model. `found_by`
    stays `classifier`.
  - An `llm` rule's finding is "found by" the model, and `found_by` is `judge`.
  - So it is always clear that a model raised it, and which one.

**Which calls.** Version 2 judges calls stored from its own release. Calls version 1
judged keep their answers and findings. Today the engine runs every current version on
every call it has not run on, which would judge old calls again against Dmytro's "New
calls only". So the spec check gets a start for each version.

**Failures and budget.**

- A failed LLM request fails the call's answer like any model check. It is tried again
  on later passes and recorded as broke after 3 attempts. The retry asks the classifier
  again; at today's volume that costs cents.
- With no `ANTHROPIC_API_KEY`, the check still runs the classifier. Flags on
  `classifier_then_llm` rules stay held and `llm` rules wait, as in 105.15. The run
  says which setting is missing.
- It shares the $1 daily model budget. A call it has not reached stays pending.

**Finding identity.** A spec finding with a moment still keeps its rule key in its
identity, so two rules broken at the same moment are two findings.

**MCP.**

- `get_call` and `get_issue` give a spec finding's moment, reason and models. The rule
  for spec findings changes: a finding has a moment and a reason when the LLM step
  gave one.
- `get_spec` renames two counts: `held_for_llm` to `confirmed_by_llm` and `llm_only` to
  `judged_by_llm`.
- The spec guide:
  - "How the rules are judged on real calls" says what each type now does.
  - Type a rule `llm` only when the classifier truly cannot judge it. Each `llm` rule
    is one more request on every judged call.
  - No check reads the prompt (decision 5). So a rule that rests on a list or a number
    written in the prompt, such as the claims the agent may make, copies it into the
    rule. This replaces 105.15's guide line that such rules are typed `llm`. It is the
    fourth thing the lab found rules missing, next to a defined term, a stated
    boundary and a stated condition.
- Contract entries for `get_call`, `get_issue` and `get_spec`.

**Screens (from the design).**

- The call screen shows a spec finding with a moment like any other finding: a mark on
  the timeline and its time. Its line gives the reason and what found it ("found by the
  classifier, confirmed by …", or "found by …").
- The issue page lists affected calls with their moment when they have one.
- Spec findings with no moment stay as 105.15 shows them.

**Docs.** `checks-and-incidents.md` (the spec check section), `issue-types.md` (the
spec row), the decision log, and the Notion "Check costs" row (an estimate now, the
production figure once real calls are judged).

## Decisions

All of Dmytro's words below are from his brainstorm in the Fable - Issues session on
2026-11-27, relayed by that session after he said "send". He took the two kinds of work
one at a time ("I dont want to even think about those types together. Lets start with
LLM verifiers"). They came out the same way: one rule, one call, one request.

1. **Build the system; the prompt is measured in the lab separately.** Decided, Dmytro
   2026-11-27: "right now we just build the system - we will work on actual prompts and
   how good they are for specific issues in lab separately". This pull request is not
   gated on a measurement.
2. **A flag is confirmed in its own request.** Decided, Dmytro 2026-11-27: "so it doesnt
   have access to prompt or multiple spec rules, just one rule. So I don't see reason
   not to do separate requests - the only thing that stays the same is inputs and call
   transcript, so I assume its not a huge number of tokens". He accepted what a request
   holds, as listed above.
3. **An `llm` rule is judged in its own request too.** Decided, Dmytro 2026-11-27: "lets
   start with separate for now".
4. **The smaller model to start, as a setting.** Decided, Dmytro 2026-11-27: "agree start
   with smaller, once we have solid system we will do more work on evals harness we have
   here and will do experiments once we get decent dataset". The smaller model
   discussed was Claude Haiku 5.5. The brainstorm assumed the test-run judge runs on
   `gpt-4.1`; it runs on Claude Haiku 5.5 already (`SIMULATION_MODEL`), so the product
   keeps one judge model.
5. **The agent's prompt is never given.** Decided, Dmytro 2026-11-27: "I lean towards
   principle that overall we use prompt only as prerequisite for spec, and then
   everything we do is 100% based on spec so all our effort should go into spec and
   with it the theory is that we can do 100% good work". This is wider than this row:
   no check reads the prompt. A rule that rests on facts in the prompt carries them.

Agreed as proposed in the brainstorm (Dmytro said "send" without changing them):

- A dismissed flag is stored and shown nowhere until false positives can be marked.
- Who found it: "found by the classifier, confirmed by" the model, or "found by" the
  model for an `llm` rule.
- Version 2 judges only calls stored from its release ("New calls only").

Proposed, not asked:

- **The LLM does not see the classifier's score.** It was in what Dmytro accepted for a
  request.
- **Without the LLM's key, the classifier part still runs.**
- **The rule comes last in a request,** so a call's requests start the same way.

## Done when

- A judged call's flags at 0.8 and above on `classifier_then_llm` rules each go to the
  LLM in a request of their own. A confirmed one is a finding with its moment and
  reason; a dismissed one is stored and raises nothing.
- Every `llm` rule is judged on every judged call, in its own request, given its named
  inputs, long ones included.
- No request holds the agent's prompt, another rule or the classifier's score.
- A finding whose ids are not in the call falls back to the whole call.
- Calls judged by version 1 keep their findings; version 2 judges calls from its
  release on.
- With no LLM key, the classifier part runs and the rest waits, saying which setting is
  missing.
- `get_call`, `get_issue` and `get_spec` answer as above, and the contract tests pass.
- The screens show spec findings with a moment as the design does.
- Tests on invented calls cover each of these, with the LLM mocked for timeout, empty
  and malformed answers.

## Out of scope

- Measuring the prompt and the model on labelled calls (lab work, decision 1).
- Marking a finding a false positive, and resolving a doubtful one with the person
  (105.17).
- Judging old calls again on request (a later, explicit action).
- Routing rules by their verdicts, where a trusted rule skips the LLM step. The
  assistant sets each rule's type for now.
- Retyping the existing 103 rules. That is the assistant's work under the guide.
- Changing the test-run judge's model.

## Risks

- **Cost grows with each `llm` rule.** These are estimates from the lab's token counts,
  not measured, with Haiku 5.5:
  - Verifying flags: about 600 to 1,000 tokens in and under 100 out per request, and
    about one flag every two calls at the 0.8 bar. That is roughly $0.05 per 1,000
    observed minutes.
  - Each `llm` rule: roughly $0.10 per 1,000 observed minutes, since it is one request
    on every judged call.
  - The classifier, for comparison: $0.21 per 1,000 observed minutes.
  A workspace with several `llm` rules reaches the shared $1 daily budget sooner.
- **A wrong dismissal is silent,** since dismissed flags are shown nowhere. It is the
  first thing the lab should measure once the step runs.
- **The LLM makes its own mistakes.** In the lab's first try, a small model said a tool
  was never called when it was. One rule per request and a reason before the verdict
  are the guards here; the lab measures the rest.

## Outcome

### Deviations from the plan

- **"Version 2 judges calls from its own release" became "a call is judged once".**
  - The spec check sets `ModelCheck.answers_carry_over`, so a version reads the answer
    an earlier version stored instead of asking again (`crud.earlier_model_answer`).
  - A call version 1 judged keeps its findings, and its held flags stay held.
  - A call version 1 never reached (pending, or behind the budget) is judged by
    version 2, LLM step included.
  - This is "New calls only" read as Dmytro wrote it, without a per-version start
    time.
- **One judge model, not two.** The brainstorm assumed the test-run judge runs on
  `gpt-4.1`. It already runs on Claude Haiku 5.5 (`SIMULATION_MODEL`), which is the
  model the LLM step starts with.
- **The LLM step uses the existing judge helper** (`checks/judge.py`, `ask_judge`). It
  already prices Haiku 5.5 for the daily budget, since LiteLLM cannot price it yet.
- **From the review:**
  - A call's LLM requests are bounded together at 30 s and asked 4 at a time.
  - A failed attempt keeps the cost of the requests that were billed (`AskFailed`),
    so the daily budget sees it.
- **Finding detail:** `model` is the model that found it, `confirmed_by` the LLM that
  confirmed a classifier flag, `reason` the LLM's words. An `llm` rule's finding is
  `found_by` judge and has no `probability`.
- **The answer names a missing LLM key** (`llm_missing`) instead of the call check's
  `missing` field, because the classifier part did run.
- **Three new MCP fields:** `found_how` on `get_issue`; `whole_call`, `reason`, `model`,
  `confirmed_by` and `entry_indexes` on `get_call` findings; `reason` on `get_issue`'s
  affected calls.

### Review (`/code-review`)

- **Fixed, important:**
  - A slow LLM could make the whole answer run out of the pass's time, so its spend
    went unrecorded and the call was asked again every pass.
  - A failed attempt dropped the cost of the requests that had been billed.
- **Fixed, small:**
  - requests per call are capped at 4;
  - a dated model id now reads as "Claude Haiku 5.5";
  - the `detail` rule in `base.py` now allows a model's reason;
  - a `get_call` next step repeated itself.
- **Not done:** the LLM step's tests replace `call_llm` instead of mocking Anthropic's
  HTTP with respx. They cover timeout, empty and malformed answers at that level, as
  the test-run judge's tests do.

### Not done

- **Measuring the prompt and the model** is lab work (decision 1). No cost is measured
  yet. The estimate is about $0.05 per 1,000 observed minutes to confirm flags, plus
  $0.10 for each `llm` rule.
- **Whether `ANTHROPIC_API_KEY` is set where the app runs** is a cloud setting, not
  checked here. Without it the classifier part runs, flags stay held and `llm` rules
  are not judged, so those calls are not judged again later.
- **Nothing to see on live data yet.** All 103 hosted rules are `classifier`. The LLM
  step acts only once the assistant types a rule `classifier_then_llm` or `llm`.
